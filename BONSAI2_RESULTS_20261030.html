Three things moved results in this period, and only one of them was code in this branch:

  1. This branch's own work (10-17): +10.0% decode, measured as a same-session A/B.
  2. Newer OpenVINO (PR head, then master): about −1.5% decode for ggml-openvino. GenAI prefill improved.
  3. Syncing with dev_backend_openvino: neutral on this model (+0.4%).

  • Decode gap to native closed 1.12x -> 1.10x. That is all of this branch's work, net of the newer OpenVINO costing ggml-openvino about 1.5%.
  • The pp512 gap to native widened 1.19x -> 1.27x. This is not a regression on our side (ggml-openvino pp512 stays at 527-544 throughout). The native reference improved: first from the tool change, then from OpenVINO master.
  • Decode against Vulkan went from a tie to a 4-6% lead. The original report called decode a tie on an ~80 GB/s bandwidth wall; this machine actually peaks at 153.6 GB/s, and ggml-openvino now decodes faster than Vulkan even though Vulkan got its own driver uplift.

What moved decode, step by step

Each row is a same-session A/B, which is the only kind of comparison here free of machine-level drift:

step change tg128 delta

M1 -> M2 OpenVINO PR 5c6d4692ee -> 4185ce2f15 (same llama.cpp) 13.47 -> 13.21 −1.9%
M2 -> M3 OpenVINO master, same llama.cpp 13.21 -> 13.23 ≈0
M3 dev_backend_openvino sync, same OpenVINO 13.23 -> 13.28 +0.4%

Why the remaining gap exists

Unchanged by anything since 10-17, and documented in detail in BONSAI2_TERNARY_OV_REPORT.md §4.1:

  • The GPU is ~100% busy on both paths (xe-PMU compute occupancy), so the gap is not host dispatch and not idle time.
  • The ternary GEMVs are identical on both paths and already reach 106 GB/s, 69% of peak.
  • The whole difference is non-GEMV graph overhead. Its largest piece is the GatedDeltaNet recurrent state crossing the f32/f16 boundary every token: 48 Convert + 96 Result per token, ~3.4 ms. ggml owns that state in f32, so removing it needs a device-resident recurrent state rather than a local change.

Measurement notes

  • Decode must be measured with -n alone on the OpenVINO backend. -p … -n … contaminates the first decode cell (OpenVINO compiles per token count). Vulkan is immune: the combined and separate runs agree to 0.2%.
  • Cross-date comparisons carry machine drift. The Vulkan step shows a driver can move results by several percent with identical code. Claims about this branch's effect come from same-session A/Bs only.
  • Two knobs were renamed in this period, and both old names are silently ignored: OV_TERNOCL_INT2_INT8_PREFILL -> OV_GPU_TERNOCL_INT2_INT8_PREFILL (OpenVINO), and GGML_OPENVINO_DISABLE_KV_SLICE=1 -> GGML_OPENVINO_KV_SLICE=0 (llama.cpp). The latter no longer affects Bonsai decode.
  • On current OpenVINO, check TernOCL is live by speed. OV_TERNOCL_INT2_DEBUG no longer exists, and the accept/reject trace needs a debug-caps build. TernOCL off is ~1.4 t/s prefill.
  • cavusmustafa/openvino master is a stale June mirror without the PR. Build upstream openvinotoolkit/openvino master.

Next steps

  1. Device-resident GDN recurrent state (~+4.7%, to ~14.0 t/s; would take the decode gap to native to ~1.04x). The hard part is correctness when llama.cpp clears and copies state slots through the compute graph. GGML_OPENVINO_STATEFUL_EXECUTION=1 does not cover recurrent state.
  2. Bisect the ~1.5% decode loss between OpenVINO 5c6d4692ee and master.
  3. PTQ1_0 support (Bonsai 1) in ggml-openvino. OpenVINO's GGUF frontend has it, with reference vectors.
  4. Prefill against GenAI (pp512 1.27x) has widened. Worth a profile to see whether it is graph overhead again or something GenAI's pipeline does differently at prefill.
  5. Upstreaming is still blocked: PQ2_0 is PrismML-fork-local, so the ternary work cannot go to dev_backend_openvino until those types land in llama.cpp master, or it goes to PrismML instead.
